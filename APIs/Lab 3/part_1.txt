##Exercise 1##
1. If every phase is set to be very long and monolithic, if something falls apart in a new step, all the exhaustive work before can fall apart altogether very quickly.
2. Lack of client feedback and input means that you presume they will be content with the final product. This is a great risk in technology, where standards can change rapidly.

##Exercise 2##
1. [Working with the customer] - Instead of presuming that the client will be sufficient with the dashboard you have developed, 
where you might have bias about how it should look, you keep the dialogue going with them so your presumptions about their needs aren't enforced.
2. [Software that works] - Apps that are used by a great number of people allow you to mostly use your intuition to use or figure
out what can be done. If Instagram had an entire manual for how to use it, there wouldn't be doomscrolling or easy navigation from videos to messaging.

##Exercise 4##
The request from the CEO should be treated as one of however many that are currently inserted into the product backlog.
It will be the responsibility of the Product Owner to add it, and when the new sprint starts, it can start becoming prioritized.
Otherwise it will be in the way of the review and retrospective. So, take it during the Sprint Planning.

##Exercise 5##
Sprint Review: Concerned about the product and implementations. Positives and negatives.
Sprint Retrospective: Concerned about the workflow. What hinders the development from excelling?

Ideally, everyone part of the Scrum team is involved for the sake of transparency.
The work of the developers is a reflection of the product owner & scrum master, and the same thing the other way around.

##Exercise 6##
a) As a user, I want a login feature added, so that I don't have to store all my history and data both manually and locally.
b) As a user, I want to be able to export all of my orders to Excel, so that I can keep track of and sort my finances in one place.

##Exercise 7##
Acceptance criteria for "As a customer, I want to see my order history, so that I can buy the same thing again."
1. Order history is presented without faults when requesting access.
2. Order displays order id, personal and delivery information, and items with their quantity price.
3. Redirection available to resource where the specific item is.

##Exercise 8##
(Since there is no specification about what the project is about, this will be pretty general.)
1. All code has been reviewed by at least one member.
2. All code has full coverage testing within its current state.
3. No critical bug or vulnerability is found during testing.
4. Proper documentation is provided for all methods.
5. End user cannot access application without login and (specified) authentication.

##Exercise 9##
45 minutes for a Daily Scrum takes a lot of time that can be used for continuing the development/product.
If the Daily Scrum is this long, chances are everything already went wrong in the Sprint Planning.
It is more of a catch-up for everyone to get a general sense that things are going as planned, or if there are any concerns that
can be dealt with together. If you already have a plan everyone has agreed and feel like they can follow, save 
all the bigger thoughts for the Retrospective, so it can be aggregated, sorted and more easily understood across the entire team.

##Exercise 10##
a) Scrum. A mobile app consists of many steps and parts in order to be developed to something complete. If it is to be built by a team, division of workload will most likely work more smoothly in sprints.  
b) Kanban. I believe that while a ticket may not just be as linear as it explains, I want to imagine that IT support focuses on one thing, and they are ticked off one by one.
c) Most likely Kanban. If the webshop is live, it should have been argued stable enough to be worth having up. Bugs will most likely be discovered in the meantime.
This question really depends on the vulnerability that the bug causes.
